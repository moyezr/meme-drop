# MemeDrop Production Release Checklist

This checklist is the minimum bar before submitting MemeDrop to the Chrome Web Store or opening the backend to public traffic.

For the final production values and Web Store handoff sequence, use `LAUNCH.md`. This file focuses on release engineering gates; `LAUNCH.md` focuses on external launch inputs such as the real API origin, Chrome Web Store extension ID, hosted privacy policy, and store screenshots.

## Current Launch Status

- Extension release builds are guarded against localhost API origins.
- Public launch status requires the final Chrome Web Store extension ID in backend CORS.
- Runtime meme templates are limited to verified templates by default.
- Backend has CORS allowlisting, request body limits, route input validation, install-aware rate limits, and guarded image downloads.
- Backend request data is isolated by an anonymous per-install ID generated by the extension.
- Users can delete this install's saved library and usage history from the popup.
- Remaining launch blocker for a broad public launch: anonymous install IDs are not real authentication and can be reset by reinstalling the extension.

Do not treat this as production-ready for a broad public launch until account/session identity, stronger abuse controls, and lawyer-reviewed privacy terms are resolved.

## Backend

Required production environment:

```bash
NODE_ENV=production
DATABASE_URL=postgresql://...
OPENROUTER_API_KEY=sk-or-...
OPENROUTER_SITE_URL=https://your-production-api.example
OPENROUTER_APP_NAME=MemeDrop
MEMEDROP_CORS_ORIGINS=chrome-extension://<published-extension-id>
MEMEDROP_RATE_LIMIT_WINDOW_MS=60000
MEMEDROP_RATE_LIMIT_MAX=600
MEMEDROP_EXPENSIVE_RATE_LIMIT_WINDOW_MS=60000
MEMEDROP_EXPENSIVE_RATE_LIMIT_MAX=180
MEMEDROP_RATE_LIMIT_STORE=database
MEMEDROP_REQUIRE_INSTALL_ID=true
MEMEDROP_CAPTION_TIMEOUT_MS=3000
MEMEDROP_USE_DRAFT_TEMPLATES=false
MEMEDROP_LOG_LEVEL=info
MEMEDROP_SUGGESTION_LOGS=compact
MEMEDROP_SUGGESTION_LOG_TEXT=redacted
MEMEDROP_IMAGE_DOWNLOAD_TIMEOUT_MS=10000
MEMEDROP_MAX_IMAGE_BYTES=8388608
MEME_STORAGE_PATH=/var/lib/memedrop/memes
```

Backend deployment checklist:

1. Run Postgres with pgvector enabled.
2. Run `npm run db:init` against the production database only after verifying `DATABASE_URL`. This enables pgvector, pushes Drizzle schema, applies compatibility migrations such as the expanded `usage_events.action` constraint, and seeds baseline data.
3. Serve `/memes/*` from persistent storage, not an ephemeral container filesystem.
4. Set `MEMEDROP_CORS_ORIGINS` to the final Chrome extension origin after the Web Store item ID exists.
5. Put the API behind HTTPS.
6. Keep `MEMEDROP_REQUIRE_INSTALL_ID=true` in production.
7. Keep `MEMEDROP_SUGGESTION_LOG_TEXT=redacted` in production; do not log full tweet text outside short-lived debugging.
8. Replace anonymous install IDs with real account/session identity before broad launch.
9. Keep `MEMEDROP_RATE_LIMIT_STORE=database` for multi-instance deployments, or replace it with platform/edge limits that cover all instances.
10. Keep image downloads restricted to public `http(s)` image URLs with DNS/private-IP checks enabled.
11. Use `/live` for container liveness probes and `/health` for readiness probes that require database connectivity.
12. Preserve `x-request-id` from upstream gateways when present; the API echoes a safe request ID on every response for support/debugging.
13. Install production deployments with dev dependencies omitted after build/migration steps, for example `npm ci --omit=dev`, so Drizzle/Vite/esbuild tooling is not shipped in the runtime image.

Production env preflight:

```bash
npm run quality:production-env
```

Run this with the real deployment environment loaded. It fails on common launch hazards such as localhost/placeholder origins, memory-only rate limits, missing install ID enforcement, full tweet-text logging, draft template exposure, and relative meme storage paths.

Production backend image:

```bash
docker build -f Dockerfile.backend -t memedrop-backend:local .
npm run quality:backend-image
```

The backend image is multi-stage: it installs dev tooling only in the build stage, compiles `shared` and `backend`, prunes dev dependencies, and runs `node backend/dist/server.js` as the non-root `node` user. Mount persistent storage at `/var/lib/memedrop/memes` or override `MEME_STORAGE_PATH` with another absolute path.

Single-host Docker Compose example:

```bash
cp .env.production.example .env.production
docker compose --env-file .env.production -f docker-compose.production.example.yml build backend
docker compose --env-file .env.production -f docker-compose.production.example.yml up -d
```

`docker-compose.production.example.yml` is an operations template, not a substitute for a managed production platform. Put a real TLS reverse proxy or load balancer in front of `backend`, keep the backend port bound to localhost/private networking, use managed Postgres if available, and back up both the database volume and meme asset volume. Run `npm run quality:production-env` with the same environment values before deploying.

## Extension

Local development build:

```bash
npm run build:extension
```

Validated release build:

```bash
VITE_API_BASE_URL=https://your-production-api.example npm run build:extension:release
```

Validated release package:

```bash
VITE_API_BASE_URL=https://your-production-api.example npm run package:extension:release
```

The package command writes `.memedrop/memedrop-extension-v<version>.zip` and validates the zip contents after creation. The package validator checks the root manifest, production API host permission, X/Twitter host permissions, icon entries, extension version, storage permission, and rejects localhost permissions, source `.ts/.tsx` files, sourcemaps, `.DS_Store`, and `__MACOSX` entries.

CI also runs the package command with a placeholder HTTPS API origin and uploads the validated zip as a workflow artifact. Use a real production API origin for any package submitted to the Chrome Web Store.

Store-readiness metadata check:

```bash
npm run store-listing:init -- \
  --privacy-policy-url https://your-production-site.example/privacy \
  --support-email support@your-production-site.example
npm run quality:store-readiness
node extension/scripts/validate-store-readiness.mjs --strict --file extension/store-listing.json
MEMEDROP_CORS_ORIGINS=chrome-extension://<published-extension-id> \
  VITE_API_BASE_URL=https://your-production-api.example \
  npm run launch:status
```

The initializer creates `extension/store-listing.json` from the tracked example and refuses placeholder privacy URLs or support emails by default. The non-strict command validates the tracked listing template and current manifest shape. The strict command is for public submission and requires a real hosted privacy policy URL, support email, screenshots, and no privacy placeholders.
Listed screenshots must be PNG or JPEG files sized `1280x800` or `640x400`, and at least one screenshot must be `1280x800`.

`npm run launch:status` is intentionally stricter than CI promotion checks. It fails until the real production API origin, hosted privacy policy/listing metadata, screenshot files, and other public-launch inputs are present.

Before upload:

1. Confirm `extension/manifest.json` uses only required permissions.
2. Confirm `storage` is disclosed as storing the anonymous install ID used to isolate library and usage data.
3. Confirm `dist/manifest.json` includes the production API host permission and no localhost permissions.
4. Test the packaged extension by loading `extension/dist` in Chrome.
5. Verify suggestion, caption, insert, save-to-library, and usage logging flows on `https://x.com`.
6. Bump `extension/package.json` and `extension/manifest.json` versions together; `npm run quality:promotion` enforces this.
7. Capture store screenshots from the real extension flow and save them under `extension/store-assets/` using the paths listed in `extension/store-listing.json`.

## Quality Gates

Run these before every release candidate:

```bash
npm run quality:promotion
npm run quality:security
npm run quality:benchmark
npm run quality:dataset-plan
MEMEDROP_SUGGESTION_LOGS=compact npm run quality:suggestions
```

CI-safe release dry run:

```bash
npm run release:dry-run
```

Strict public release candidate:

```bash
VITE_API_BASE_URL=https://your-production-api.example npm run release:candidate
```

The dry run uses the placeholder HTTPS API origin and verifies build/package mechanics. The strict candidate additionally requires the real backend production environment, strict Chrome Web Store metadata, fast suggestion quality, and public launch status. Both commands rebuild `extension/dist` back to the local development API configuration after packaging.

`quality:security` requires the production dependency audit to be clean. It allows only documented development-install advisories for build/migration tooling that is excluded from runtime deployments with `npm ci --omit=dev`.

CI also runs `npm run quality:backend-image` as a separate job so the production Docker runtime is built and smoke-tested independently of the extension release artifact.

Expected current template gate:

- `npm run manifest:audit --workspace=backend` should report zero errors.
- The review queue should be empty or contain only intentionally deferred drafts.
- Fast suggestion eval should pass the configured top-k, caption, layout, and overlay thresholds.
- `npm run quality:compiled-backend` should build shared/backend and prove `node backend/dist/server.js` can start from compiled JavaScript.

Dataset promotion flow:

```bash
npm run dataset:qa-expansion
npm run dataset:review-decisions:init
npm run dataset:review-decisions
npm run dataset:promotion-plan
npm run dataset:benchmark-stubs
npm run dataset:benchmark-import -- --file .memedrop/suggestion-benchmark-stubs.json
npm run dataset:review-decisions:promotion
npm run quality:dataset-plan
npm run dataset:promote-reviewed
npm run quality:promotion
MEMEDROP_SUGGESTION_LOGS=compact npm run quality:suggestions
```

Only promote reviewed templates in small batches. The promotion planner writes `.memedrop/template-promotion-plan.json` and identifies ready approvals, blocked approvals, unreviewed clean drafts, and benchmark-case stubs. The promotion compiler writes `shared/src/data/meme-template-manifest.promoted.json`; runtime lookup includes those templates only after they are marked `verified` by the compiler.

## Chrome Web Store

Use the current official Chrome Web Store documentation as the source of truth:

- Program policies: https://developer.chrome.com/docs/webstore/program-policies
- Publish flow: https://developer.chrome.com/docs/webstore/publish
- Privacy fields: https://developer.chrome.com/docs/webstore/cws-dashboard-privacy
- User data FAQ: https://developer.chrome.com/docs/webstore/program-policies/user-data-faq

Submission checklist:

1. Register and verify the Chrome Web Store developer account.
2. Prepare screenshots that show the suggestion panel, meme preview, and inserted meme reply.
3. Write a narrow single-purpose description: helping users create meme replies on X.
4. Fill out privacy practices to match the actual data flow.
5. Link a hosted privacy policy.
6. Disclose the X/Twitter host permissions and production API host permission.
7. Start with private or unlisted tester distribution before public listing.
8. After the Web Store item ID is assigned, update backend CORS with `chrome-extension://<id>`.

## Privacy And Data Handling

Current data flow:

- Tweet text from the active compose context is sent to the MemeDrop backend to generate suggestions and captions.
- A random anonymous install ID is stored in Chrome extension storage and sent with backend requests to separate user libraries and usage events.
- Meme IDs, generated tweet context, and usage events are sent to the backend for quality and personalization. Usage events include shown, clicked, inserted/used, saved, and dismissed meme events.
- Saved meme images are downloaded by the backend and stored in `MEME_STORAGE_PATH`.
- The backend sends prompt content to OpenRouter for analysis, embeddings, captioning, and image tagging.

Required before public launch:

1. Host `PRIVACY.md` or a lawyer-reviewed replacement on a public URL.
2. Make in-product/store disclosures match the hosted policy.
3. Decide retention periods for tweet text, derived context, usage logs, and saved images.
4. Keep `DELETE /api/v1/account` and `GET /api/v1/account/export` working for anonymous installs.
5. Add account deletion/data deletion flow again if real user accounts are introduced.
6. Avoid collecting unrelated browsing activity.

## Known Gaps

- Anonymous install IDs are not strong authentication and do not survive extension reinstall.
- Deletion/export is scoped to the current anonymous install ID only.
- Rate limits are distributed when `MEMEDROP_RATE_LIMIT_STORE=database`; the local default remains in-memory for development.
- Image download SSRF protection rejects local/private literal hosts, private DNS resolutions, redirects, non-image responses, and oversized files. It is still not a full network egress firewall.
- No formal unit/integration test framework yet.
